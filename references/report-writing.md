# 可逐步更新的中文 Markdown 报告

`report.md` 是供人阅读的调查工作文档，**新建、续写和修订均使用简体中文**。初始化器只提供少量起始标题；可根据案件增删章节。页首可见的“采集包 SHA-256”行用于绑定唯一证据包，修改报告结构时须保留该行。文本使用 UTF-8，每个采集包各有独立报告目录。

## 让读者快速理解

- 开头用两三句日常语言写明：已确认什么、哪些仍是疑点、目前可采取什么决定。标注状态和更新时间，不以七张来源表或冗长 IOC 列表开篇。
- 按事件时间讲述经过，并标明时区。每个环节说明哪个对象做了什么、涉及哪条路径或网络端点，以及哪条记录支持该说法。技术字段可放在简短证据列表或附录。
- 明确区分**已观察**、**推断**、**未验证**和**已排除或降权的噪声**。扫描命中只证明扫描器命中；下载记录只证明浏览器记录的状态；单独的 Prefetch 或 Amcache 不证明其后的全部行为。会影响结论的替代解释也应写出。
- 重要判断应附最少量但足够的引用，例如 `browser_downloads:42` 或 `native_artifacts:180`，并说明缺失环节与信心程度。引用中的数字是 SQLite 数据库内从 1 开始的 JSONL 行号；用页首来源哈希区分其他采集包里的相同 ID。
- 第一次出现术语时说明含义。例如先写“签名程序从同目录加载可疑 DLL”，再使用“DLL 侧载”。路径、时间和行为概述通常比整段原始 JSON 更便于阅读。
- 将重复、低价值记录合并为数量或模式，正文突出少量决定性样例；完整 IOC、查询细节和解析异常可放附录。原版 JSON 最多展示 32 条详情的限制不应截断 Markdown 的案情。
- 将发现转为可执行的下一步：需要保全或验证什么、当前可处置什么、获得哪类证据会改变判断。涉及新取证或处置时说明所需证据和授权前提。

## 更新时保持前后一致

新增证据后，直接修改页首当前判断及受影响的证据链，再在更新记录写明时间、变化和原因；被降级或撤回的判断也要记录。未解决问题保留到确实得到答案。调查中可以标记“分析中”，不要为了生成完整格式而伪造完成状态。只有完成来源覆盖和最后一次证据复核后，才标记本轮分析完成。

`report.json` 是审查完成后的结构化配套文件。原版 Schema 要求 `current_stage: 完成` 和 `progress: 100`，因此调查未完成时不要制造一份形式上已完成的 JSON。最终交付前，人工核对两份报告的重要结论、不确定性和来源 SHA-256。检查脚本只验证结构和引用是否存在，无法验证语义是否一致。
